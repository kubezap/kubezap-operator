# Secret rotation detection for gateway watchers

## Problem Statement

Webhook Trigger auth secrets (HMAC/bearer/basic/apiKey/header-equals — `internal/gateway/webhook/watcher.go`) and Kafka/AMQP/NATS broker credentials (SASL/TLS, resolved via the referenced `Integration` — `internal/gateway/{kafka,amqp,nats}/watcher.go`) are read once, via a direct (uncached) `client.Get` call, at the moment the gateway processes a Trigger add-or-update event. The resolved value is then held in memory indefinitely: in the webhook gateway's `RouteRegistry` entry, or in the kafka/amqp/nats gateway's `subscription` entry.

No reconciler or watcher in the codebase sets up any kind of watch on `Secret` objects — confirmed by grep across `internal/controller/` and `internal/gateway/`. If ESO (or any external rotation mechanism) updates a Secret's data without touching the Trigger or Integration that references it, the gateway keeps using the stale credential indefinitely, until something else causes that Trigger to be reconciled again (an unrelated spec edit) or the gateway pod restarts. For HMAC/bearer/API-key secrets this means webhook requests signed with the *new* key are rejected until the stale route entry is refreshed. For Kafka/AMQP SASL credentials this means the broker connection eventually fails authentication and the consumer stops receiving events, silently, until the pod is restarted.

**Related, more severe bug found while researching this fix**: the kafka/amqp/nats gateways' shared `kubezap-gateway` Role (`internal/controller/integration_controller.go`, three near-identical `Role` builders) grants **no `secrets` permission of any kind** — not `get`, not `list`, not `watch`. `readSecretKey`'s direct `client.Get` call for SASL username/password and TLS CA secrets must therefore already be failing with `Forbidden` in any real cluster where those fields are actually set. This has apparently gone unnoticed because every live E2E validation of `kafka-enrichment`/`dlq-handler` this project has run used a plaintext, unauthenticated Strimzi cluster (SASL/TLS fields unset — the code path that would hit this permission was never exercised). This is a genuine prerequisite: adding `list`/`watch` for a Secret informer is meaningless if even `get` doesn't work today. This design fixes both problems together, since the RBAC rule needs is a strict superset either way.

## Constraints

- **RBAC minimum**: grant exactly the verbs required (`get`, `list`, `watch` on `secrets`, scoped to the gateway's own namespace via the existing per-namespace `Role`/`RoleBinding` pattern) — no cluster-wide secret access, consistent with the project's least-privilege posture (`CLAUDE.md`: OwnNamespace/SingleNamespace use `Role`, not `ClusterRole`).
- **No new external dependency.** The fix uses the same `sigs.k8s.io/controller-runtime/pkg/cache` (`crcache.Cache`) each watcher already constructs for its `Trigger` informer — adding a second informer for `corev1.Secret` on the same cache, not a new watch mechanism.
- **Must not change existing dedup/idempotency behavior for real Trigger/Integration spec changes.** `kafka`/`amqp`/`nats` watchers already skip restarting a subscription when `topic`/`consumerGroup`/`integrationName` are unchanged (`reconcileTrigger`) — this fast path must keep working for changes unrelated to credentials.
- **Must not require watching `Integration` objects.** Credentials for kafka/amqp/nats triggers are reached via `Trigger.Spec.Kafka.IntegrationRef` → `Integration.Spec.Kafka.{SASL,TLS}.*SecretRef`, resolved via a direct (uncached) `client.Get` for the `Integration` on every Trigger event. Watching `Integration` too would double the scope of this change for a problem (Integration spec drift) that is a *different*, rarer gap than the one asked for here (secret *value* rotation) — out of scope, noted under Rejected Alternatives.
- **Idempotent, safe to run concurrently.** The informer's Secret-change callback and the Trigger-change callback can fire on different goroutines; the reverse index must be safe for concurrent read/write.

## Invariants

- A Secret referenced (directly, by a webhook Trigger's auth config, or indirectly, by an Integration a kafka/amqp/nats Trigger's `IntegrationRef` points at) by at least one currently-`Enabled` Trigger is being watched, and any change to its `.data` causes every Trigger that references it to be reprocessed within one informer resync (no polling, no restart required).
- A Secret referenced only by Triggers that are deleted, disabled, or no longer reference it must not remain in the reverse index — stale entries do not accumulate unboundedly across the gateway's lifetime (same shape of concern as §23's `cooldownTracker` unbounded-growth fix).
- Reprocessing a Trigger because a referenced Secret changed must go through the exact same code path as a real Trigger spec change (`handleTrigger` for webhook, `reconcileTrigger` for kafka/amqp/nats) — no second, parallel "credential refresh" code path that could drift from the primary one.
- For kafka/amqp/nats: a credential-only change (Secret content changes, `topic`/`consumerGroup`/`integrationName` do not) must still result in the consumer group being torn down and restarted with the new credentials — the existing "no change" fast path in `reconcileTrigger` must not silently swallow a credential rotation.
- No new Secret value (its bytes) is ever logged — the same rule the codebase already applies everywhere else secrets are touched (`RouteEntry.redactedForLog()`, §26 P2 fix).

## Rejected Alternatives

**Poll Secrets periodically (e.g. a ticker that re-fetches and re-diffs every N minutes) instead of watching.** Rejected: strictly worse on every axis than a proper watch — adds rotation-detection latency up to the poll interval, adds constant API server load even when nothing changes, and the project already has a working, idiomatic pattern (the existing `Trigger` informer) to extend rather than introduce a second, different mechanism next to it.

**Also watch `Integration` objects, so an Integration's `secretRef` fields (not just the Secret's contents) changing is detected too.** Rejected for this change: it's a real but *different* gap (Integration spec drift, not secret rotation) with its own reverse-indexing question (Integration → which Triggers reference it, already partially resolved by existing `IntegrationRef` lookups) — bundling it in would double this design's surface area for a problem the owner didn't ask about. Left as an explicit, named follow-up rather than silently expanded scope.

**Extract a shared `internal/gateway/secretwatch` package used by all four watchers**, rather than implementing the informer registration and reverse index natively in each file. Considered, since the logic is close to identical across `kafka`/`amqp`/`nats` (byte-for-byte identical `NewWatcher`/cache-setup boilerplate already exists across those three) and there's already one precedent for a tiny shared gateway package (`internal/gateway/redact`, used by kafka/amqp/webhook). **Rejected in favor of native duplication**, because the four watchers' credential shapes are not actually identical at the point the index needs to be built (webhook has 6 inline auth-type branches on the Trigger itself; kafka/amqp/nats resolve through an `Integration`'s SASL/TLS config) — a shared abstraction would need to expose a callback-heavy interface to accommodate both shapes, which is more complexity than the ~30 lines of duplicated informer-registration boilerplate it would save. The existing `internal/gateway/redact` precedent is a pure, stateless helper function; this reverse index is stateful and per-watcher, which fits the existing "duplicate small watcher-lifecycle code, share only pure helpers" pattern already established by kafka/amqp/nats's near-identical `NewWatcher` rather than breaking it.

## Tradeoffs

- **Slightly more memory per gateway pod**: an additional informer cache for `Secret` objects in the watched namespace(s), plus a small reverse-index map. Bounded by the number of distinct Secrets referenced by enabled Triggers/Integrations in scope — not a concern at any realistic scale (same class of bound already accepted for the `Trigger` informer cache itself).
- **kafka/amqp/nats gateways gain real `secrets: get/list/watch` RBAC** where they previously had none at all. This is fixing a bug (the code already assumes `get` works), not a new privilege being granted for a new purpose — but it is a materially larger permission grant than exists today (currently: zero secret access, silently broken).
- **Credential-fingerprint comparison adds a small amount of CPU per Trigger reconcile** (hashing the resolved credential bytes) to detect content-only changes — negligible next to the network I/O already happening in the same code path (the Secret `Get` call itself).

## Final Decision

Add a second informer (`corev1.Secret`, same `crcache.Cache` each watcher already owns) to all four gateway watchers. Each watcher maintains its own in-process reverse index (`map[secret NamespacedName][]trigger NamespacedName`, mutex-protected), rebuilt for a given Trigger every time that Trigger is reconciled (so stale references are dropped automatically as part of the existing reconcile flow, not a separate GC pass). On a Secret add/update event, look up affected Trigger keys in the index and re-invoke the exact same per-Trigger reconcile function already used for real spec changes (`handleTrigger` for webhook; `reconcileTrigger` for kafka/amqp/nats), using the Trigger informer's already-synced local store to fetch the current object (no extra API call).

For kafka/amqp/nats, extend the `subscription` struct with a `credentialFingerprint` (SHA-256 of the resolved SASL/TLS material) alongside the existing `topic`/`consumerGroup`/`integrationName` fields, so `reconcileTrigger`'s existing "no change, skip restart" fast path naturally detects a credential-only rotation instead of silently ignoring it.

Fix the prerequisite RBAC gap as part of the same change: add `secrets: get/list/watch` to `desiredKafkaGatewayRole`/`desiredAmqpGatewayRole`/`desiredNatsGatewayRole`'s rule sets (currently absent entirely) and upgrade the webhook gateway's existing `secrets: get` to `secrets: get/list/watch` (`desiredWebhookGatewayRole`).

Integration-object watching (detecting a changed `secretRef` pointer, as opposed to a changed Secret value) is explicitly out of scope — filed as a follow-up item, not addressed here.
