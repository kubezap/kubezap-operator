# FlowRun Step-Timing Precision

> Status: Draft
> Related: `api/v1alpha1/flowrun_types.go`, `internal/controller/flowrun_controller.go`, `internal/metrics/metrics.go`, `benchmarks/execution-latency/RESULTS.md`, `planning/backlog/stories/STORY-020-flowrun-step-timing-precision-design.md`, `planning/backlog/stories/STORY-021-flowrun-step-timing-precision-impl.md`, `planning/backlog/stories/STORY-015-benchmark-writeup.md`

## 1. Problem Statement

`StepRunStatus.StartTime`/`CompletionTime` and `FlowRunStatus.StartTime`/`CompletionTime` (`api/v1alpha1/flowrun_types.go`) are all `*metav1.Time`, which marshals to whole-second RFC3339 (`metav1.Time.MarshalJSON` truncates to `time.Second` — this is a hard property of the type, not a bug in how KubeZap uses it). STORY-015's execution-latency benchmark (`benchmarks/execution-latency/RESULTS.md` §2.1) hit this directly: KubeZap's real per-step dispatch latency is ~5–10ms, and 594 of 600 step observations in the benchmark's raw `FlowRun.status` JSON read as an exact `0.000s`, with the remaining 6 landing on `1.000s` purely from which side of a wall-clock second boundary the step happened to fall on. The only place the true number was visible was a one-off scrape of `kubezap_step_duration_seconds`, a Prometheus histogram recorded from `time.Since()` at full precision — not something `kubectl get flowrun -o yaml`, the tool a user actually reaches for, can show at all.

The same quantization problem exists one level up: `kubezap_flowrun_duration_seconds`'s mean end-to-end duration for the benchmark's 3-step flow was 537ms (RESULTS.md §2.3), which `FlowRunStatus.StartTime`/`CompletionTime` would report as `0s` or `1s` with equal unhelpfulness.

User impact: with STORY-015's go/no-go verdict being **pursue** ("faster/lighter than Pod-per-step engines" as a stated differentiator), the one number that substantiates that claim is invisible on the object whose whole purpose is to report what happened. A user comparing KubeZap to Argo by eyeballing `kubectl get flowrun -o yaml` today sees `0s` durations that look either broken or unmeasured, not "genuinely fast."

## 2. Constraints

- **API stability (v1alpha1 → no field removals without deprecation).** `StepRunStatus.StartTime`/`CompletionTime` and `FlowRunStatus.StartTime`/`CompletionTime` stay exactly as they are, same type, same meaning (second-precision wall-clock phase-transition markers) — nothing here may remove or retype an existing field.
- **Whatever is added must come from a value the reconciler already computes**, not a new measurement path. `internal/controller/flowrun_controller.go` already computes a full-precision `time.Duration` in both places this record cares about:
  - Per step: `stepStart := time.Now()` / `dur := time.Since(stepStart)` in the wave-execution goroutine (around line 584), carried through `stepResult.duration` and consumed by `metrics.StepDuration.WithLabelValues(...).Observe(res.duration.Seconds())` (around line 643).
  - Per FlowRun: `duration := time.Since(flowRun.Status.StartTime.Time)` computed at both terminal-transition sites — the inline Succeeded path (around line 692) and the shared `finishFlowRun` helper used for Failed/Cancelled (around line 1478) — immediately before `metrics.FlowRunDuration.WithLabelValues(...).Observe(duration.Seconds())`.

  Any design that requires a *second* timing measurement (e.g. deriving a duration by re-subtracting two persisted timestamps later) is disfavored — it's redundant with data already in hand at the exact call site that already needs it for the histogram, and introduces a second source of truth that can disagree with the metric.
- **No behavior change to reconciliation, phase transitions, or existing conditions.** This is a status-schema addition only.
- **CRD regeneration discipline.** Any new field needs `make generate && make manifests` (out of scope for this record — STORY-021's job) and must show up correctly in `config/crd/bases/automation.kubezap.io_flowruns.yaml`.
- **Metrics remain canonical for cross-run aggregation.** This record is about per-object visibility (`kubectl get flowrun -o yaml`, one FlowRun at a time), not about replacing `kubezap_step_duration_seconds`/`kubezap_flowrun_duration_seconds` for p50/p95 aggregation across many runs — Prometheus stays the right tool for that; nothing here changes the metrics.

## 3. Invariants

- A `StepRunStatus`/`FlowRunStatus` whose step/FlowRun has not yet reached a terminal state (`Succeeded`/`Failed`/`Skipped` for a step; `Succeeded`/`Failed`/`Cancelled` for a FlowRun) has no duration value set — mirrors the existing `CompletionTime == nil` convention exactly; the new field's presence/absence must never disagree with whether `CompletionTime` is set.
- The persisted duration for a given step/FlowRun is always numerically consistent with (in practice, identical to, since it is written from the same in-memory value) whatever `kubezap_step_duration_seconds`/`kubezap_flowrun_duration_seconds` recorded for that same execution — no independent recomputation path is introduced that could drift from the metric.
- `StartTime`/`CompletionTime` continue to mean exactly what they mean today (second-precision phase-transition timestamps, still useful for ordering, for correlating against `kubectl get events`/external logs, and for the existing `ExecutionTimeout` check in `internal/controller/flowrun_controller.go` around lines 317–321, which truncates to `time.Second` already and needs no more precision than that) — nothing about this change repurposes or deprecates them.
- Existing `FlowRun` objects (already persisted, written before this change ships) remain valid: the new field is `+optional`, decodes as absent/zero on old objects, and no existing reader (controller, CLI, e2e test) breaks by its absence.

## 4. Rejected Alternatives

**A. Sub-second-precision timestamps — replace or augment `StartTime`/`CompletionTime` with `metav1.MicroTime` (Kubernetes' own microsecond-precision timestamp type, used e.g. by `v1.Event.EventTime`).**

This is the most credible version of option (a) — it isn't inventing a new type, it's reaching for the idiomatic Kubernetes one. Rejected anyway, for reasons specific to *this* problem rather than a general dismissal of the type:

- It answers a question nobody asked. The problem statement isn't "we don't know exactly when a step started," it's "we can't tell how long a step took." A `MicroTime` pair still forces every consumer — a human reading `kubectl get flowrun -o yaml`, a script, a future dashboard — to subtract two RFC3339 strings themselves to get the one number that matters. An explicit duration field answers the actual question directly with zero client-side arithmetic or timezone/parsing risk.
- It doesn't reuse the already-computed value cleanly. The reconciler's `time.Since(stepStart)` / `time.Since(flowRun.Status.StartTime.Time)` calls produce a `time.Duration` directly; getting from there to a pair of `MicroTime` values means capturing `stepStart` as a timestamp (already true) *and* a fresh `time.Now()` at completion, then trusting a downstream subtraction to reproduce the same number the histogram observed — two writes instead of one, and a second source of truth that could in principle disagree with the metric (e.g. if a future refactor changes one call site's clock read but not the other).
- No real per-step consumer needs absolute time. The one place in this codebase that reads a `*metav1.Time` for control flow (`ExecutionTimeout` against `FlowRunStatus.StartTime`) already works at second precision and has no analog at the per-step level today — there is no existing or planned per-step timeout/SLO check that would need a microsecond-precision `StepRunStatus.StartTime`.
- It's a larger, riskier change for no benefit here: swapping `StartTime`'s Go type is more invasive than adding a field (different marshal/unmarshal behavior, a CRD schema `format` consideration, and downstream code — CLI printers, e2e JSONPath assertions — that currently expects `metav1.Time`'s whole-second string shape would need auditing), for a capability (arbitrary two-point time arithmetic) nothing here actually needs.

**B. Sub-second precision timestamps as new additional fields (e.g. `StartTimeMicro`/`CompletionTimeMicro` as `metav1.MicroTime`, alongside the untouched existing fields).**

A softer version of A that avoids retyping the existing fields. Still rejected: it's strictly more schema surface than option (b) (four new fields instead of one or two) for the same "still requires client-side subtraction" downside as A, and doubles the timestamp footprint on every `StepRunStatus`/`FlowRunStatus` (two started-at fields, two completed-at fields) for a value nobody needs more precisely than duration.

**C. Leave `StepRunStatus`/`FlowRunStatus` alone; treat the Prometheus histograms as sufficient.**

Rejected — this is the status quo the problem statement is about. It works for cross-run p50/p95 aggregation (and should stay the tool for that — see Constraints) but not for "what did *this* FlowRun actually cost," which is what a user reaching for `kubectl get flowrun -o yaml` is asking, and what substantiates the "pursue" differentiator claim from STORY-015 on a per-object basis rather than only via a point-in-time metrics scrape.

**D. Apply the duration-field treatment only to `StepRunStatus`, leave `FlowRunStatus`'s top-level `StartTime`/`CompletionTime` untouched for now (defer to a later story).**

Considered, since the story's acceptance criteria treats this as an open question rather than a given. Rejected: the exact same evidence applies at both levels — RESULTS.md flags `kubezap_flowrun_duration_seconds`'s 537ms mean as having "the same cumulative-counter caveat" and being subject to the identical whole-second quantization if read from `FlowRunStatus` directly, and the reconciler already computes the precise `time.Duration` at both terminal-transition call sites (see Constraints) — there is no extra measurement work to defer, only a few extra lines to set a field from a value already sitting in a local variable at two well-understood call sites (the inline Succeeded path and `finishFlowRun`). Splitting this into two stories would create exactly the kind of "half the object is fixed, half isn't" inconsistency this record's own Constraints section argues against for the per-step case, for no reduction in real implementation cost.

## 5. Tradeoffs

- A `DurationMillis` field is a derived value that duplicates information already recoverable (albeit only at second precision) from `StartTime`/`CompletionTime` — accepted, because the whole point is that the precise version isn't recoverable from those fields; some redundancy between a coarse pair of timestamps and a precise duration is the intended outcome, not an oversight.
- Milliseconds as the unit loses precision below 1ms — accepted; the benchmark's own numbers (5–10ms per step) make millisecond resolution comfortably sufficient, and matching the unit already used informally throughout this project's docs/benchmarks (`RESULTS.md` reports everything in ms/s, never µs or ns) keeps the field's numbers directly comparable to those docs without a unit-conversion step for a human reader.
- `DurationMillis` as a plain integer loses the self-describing unit that a `metav1.Duration`-typed field (which marshals as a Go-duration string like `"6ms"`) would have given for free — accepted in favor of `int64` milliseconds specifically because `res.duration`/`duration` are already `time.Duration` in Go and `.Milliseconds()` is a one-line, allocation-free conversion at the exact call site that already has the value, whereas `metav1.Duration` requires wrapping (`metav1.Duration{Duration: d}`) and its human-readable string form is unnecessary for something already reported as `float64` seconds in the parallel Prometheus histogram — matching the existing convention (numeric, no wrapping) was judged more valuable than the self-describing unit here, and the field name (`durationMillis`) plus doc comment carry the unit instead.
- This does not fix the *cross-run aggregation* version of the quantization problem — a script that lists many FlowRuns and wants p50/p95 across them should still use the Prometheus histograms, not paginate through `FlowRun` objects; this field is for single-object visibility only, not a metrics-store replacement. Worth stating plainly so a future reader doesn't reach for `DurationMillis` for a job it isn't meant to do.

## 6. Final Decision

Add `DurationMillis *int64` (`json:"durationMillis,omitempty"`, `+optional`) to both `StepRunStatus` and `FlowRunStatus` in `api/v1alpha1/flowrun_types.go` — **option (b)** from the story's acceptance criteria, applied at both levels rather than per-step only. `StartTime`/`CompletionTime` are unchanged at both levels (still `*metav1.Time`, still second-precision, still the fields anything doing timeout/ordering/correlation logic should use). `internal/controller/flowrun_controller.go` sets the new field directly from the `time.Duration` value already computed and observed into the corresponding Prometheus histogram — `res.duration.Milliseconds()` where `stepResult` is folded into a persisted `StepRunStatus`, and `duration.Milliseconds()` at both `FlowRunStatus` terminal-transition sites (the inline Succeeded path and `finishFlowRun`) — so there is exactly one measurement per execution, feeding both the histogram and the new status field, with no second clock read and no possibility of the two disagreeing.

No `v1alpha2` bump is required. Per `design-process.md`'s Constraints ("API stability guarantee: v1alpha1 → no field removals without deprecation"), this change adds two new `+optional` fields and removes or retypes nothing — existing `FlowRun` objects persisted before this ships remain valid (the field decodes as absent), existing clients that don't know about the field are unaffected, and the CRD's structural schema accepts the addition as a purely additive, backward-compatible change within the same served/stored version. This is the same reasoning `docs/design/2026-09-12-webhookgatewayconfig-crd.md` isn't a counterexample of — that record introduced a *new CRD*, not an additive field on an existing one.

Implementation (STORY-021) should also confirm at code-review time that `DurationMillis` is only ever set once a step/FlowRun reaches the same terminal condition that already causes `CompletionTime` to be set — per this record's Invariants, the two must never disagree on "has this finished."
