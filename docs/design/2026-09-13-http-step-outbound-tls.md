# HTTP-Step Outbound TLS/CA Support

> Status: Approved
> Related: `api/v1alpha1/integration_types.go` (`HttpIntegrationSpec`), `internal/controller/flowrun_controller.go` (`applyHTTPIntegration`/`applyHTTPAuth`), `internal/executor/http/types.go` (`ExecuteRequest`), `internal/executor/http/handler.go` (`httpClient`), `internal/gateway/secretindex`, `docs/design/2026-03-24-security-review.md`, `docs/design/2026-09-11-secret-rotation-watches.md`, `planning/backlog/epics/EPIC-005-http-step-outbound-tls.md`, STORY-025

## 1. Problem Statement

HTTP steps (`type: http` Flow actions) have no way to trust a private or internal CA, or present a client certificate, for an outbound call. The only outbound TLS control today is `tlsSkipVerify` on `internal/executor/http/types.go`'s `ExecuteRequest`, honored only when the executor binary is started with `--allow-tls-skip-verify` — and even that field is currently unreachable: `internal/controller/flowrun_controller.go`'s `ExecuteRequest` construction (line ~887) never sets `TLSSkipVerify: true` regardless of any Flow/Trigger configuration, because nothing in the API surface exposes it (found during STORY-023, 2026-09-13).

User impact: an HTTP step targeting a service behind a private/internal CA (a common case for internal enterprise services, service meshes with custom root CAs, or self-hosted infrastructure) fails TLS verification with no fix available short of restarting the executor with `--allow-tls-skip-verify` — which disables verification for every HTTP step in that namespace, not just the one that needs a trusted private CA. This is a real, live gap: the owner confirmed directly (2026-09-13) — "I do need support for setting CA somehow for outbound http requests" — after the previously-documented fix (three `kubezap.io/tls-*` Trigger annotations) turned out not to exist in code at all (removed as fiction via STORY-023).

Meanwhile Kafka/AMQP/NATS `Integration`s already have a real, working CA/client-cert mechanism (`KafkaTLSConfig`/`AmqpTLSConfig`/`NatsTLSConfig`, each with `CASecretRef`/`ClientCertSecretRef`) — HTTP is the one Integration type this pattern doesn't reach, despite `HttpIntegrationSpec` already existing and already being the Integration-scoped home for other per-target HTTP config (`baseUrl`, `auth`, `defaultHeaders`).

## 2. Constraints

- **Executor RBAC stays minimal.** Per `CLAUDE.md`'s Runtime Architecture, `http-executor` has "Minimal RBAC (no secrets, no RBAC management)" — this is a deliberate security boundary from the 2026-03-24 security review (separate low-privilege binary, specifically so a compromised executor can't read cluster secrets). Any CA bundle / client cert resolution must happen controller-side; the executor must never be granted `get`/`list`/`watch` on `Secret` or `ConfigMap`, and must never be passed a `SecretKeyRef`/`ConfigMapKeyRef` to resolve itself.
- **Credentials never written to etcd beyond the source objects themselves.** Per `CLAUDE.md`: "credentials never written to etcd; they are resolved in-process and forwarded via internal RPC only." A resolved client-certificate private key must not be persisted anywhere except the internal `POST /execute` RPC body (not cached in `FlowRun.Status`, not logged). This mirrors the existing constraint already honored for HTTP-auth secrets (bearer tokens, API keys) resolved by `applyHTTPAuth`.
- **API stability (`v1alpha1`).** No field removals or retyping on `Integration`; only additive `+optional` fields are allowed without a version bump.
- **Consistency with the existing `Integration`-scoped TLS pattern** (`KafkaTLSConfig`/`AmqpTLSConfig`/`NatsTLSConfig`) where it doesn't conflict with the owner's explicit ConfigMap decision below — same field-naming conventions, same `LocalObjectReference`/`SecretKeySelector` shapes, so this doesn't read as a bespoke one-off.
- **Owner-mandated shape decisions** (stated directly, 2026-09-13, non-negotiable inputs to this design, not open questions):
  - The CA field must accept a **bundle** — potentially multiple trusted certificates (e.g. a private root plus intermediates, or more than one trusted root) — not a field restricted to exactly one certificate.
  - The CA bundle is sourced via `ConfigMap`, not `Secret` — "a CA bundle is public data, not a secret." This is a deliberate asymmetry from Kafka/AMQP/NATS's Secret-only `caSecretRef` convention.
- **Channel security for the RPC body itself is already handled and out of scope here** — the controller→executor channel is secured by mandatory `NetworkPolicy` plus optional mTLS (`--executor-mtls=true`); this design doesn't change or need to touch that.

## 3. Invariants

- A client-certificate private key resolved for an HTTP step's TLS connection is never written to etcd and never appears in `FlowRun.Status` or in structured logs.
- A CA bundle or client certificate configured on an `Integration` is applied **only** to HTTP steps that reference that `Integration` — never globally (never mutates a package-level default `http.Transport`/root pool shared across requests).
- Resolving the same `Integration`'s TLS configuration twice within a single `FlowRun` reconcile (e.g. two steps referencing the same `Integration`) returns byte-identical PEM content — consistent with the existing per-reconcile `Integration` cache's idempotency guarantee (`applyHTTPIntegration`'s `cacheKey` lookup).
- An HTTP step that does **not** reference an `Integration` with TLS configured behaves exactly as it does today (system root CA pool, no client cert) — this is purely additive.
- A configured CA bundle is **added to** the system root pool, not a replacement for it — an `Integration` with a private CA configured can still reach a public-CA-signed endpoint (a redirect, a public API on the same backend, etc.) without losing default trust. Implementation must clone/start from `x509.SystemCertPool()` and append the configured bundle to it, not construct an empty pool.
  - **This is a deliberate divergence from Kafka/AMQP/NATS**, whose existing `CASecretRef` handling (`internal/gateway/{kafka,amqp,nats}/watcher.go`, `flowrun_controller.go`'s Kafka publish path) all build an **empty** `x509.NewCertPool()` — configuring a CA there *replaces* system trust entirely. That's the right model for a broker connection to one fixed, known bootstrap address (no legitimate reason the same broker would also need a public-CA-signed path). It's the wrong model for HTTP steps, which target arbitrary, per-call URLs where the same `Integration` may legitimately need both private- and public-CA-signed backends. Migrating the brokers to additive-mode was considered and explicitly rejected (see Rejected Alternatives) — not done here, and not implied by this decision.
- `tlsSkipVerify`'s existing (if currently unreachable) semantics are unchanged: when set, it still means "skip verification entirely," and it is not implicitly overridden by a configured CA bundle or vice versa — the two are orthogonal, independently-settable knobs.

## 4. Rejected Alternatives

- **A new, dedicated `Integration` type for TLS material** (e.g. `type: tls`, referenced alongside the `type: http` Integration). Rejected: unnecessary indirection — `HttpIntegrationSpec` already exists as the per-target-system home for `baseUrl`/`auth`/`defaultHeaders`; a step would need to reference two `Integration`s for one backend, which no other Integration type requires and which complicates the common case for no real benefit.
- **A `Trigger`- or step-level field** (each `FlowStep` or `Trigger` carries its own CA/cert ref inline). Rejected: wrong scope, too granular. A given backend's CA/client cert is a property of the backend, not of each individual call to it — every other per-target HTTP setting (`baseUrl`, `auth`, `defaultHeaders`) is already `Integration`-scoped for exactly this reason. Step-level would mean re-specifying the same `ConfigMapKeyRef`/`SecretKeyRef` on every step that calls the same backend, inconsistent with the existing pattern and more error-prone (a typo'd ref on one of many steps silently loses TLS trust for that call only).
- **Migrating Kafka/AMQP/NATS's existing `CASecretRef` handling from "replace system trust" to "additive" (matching HTTP's new pool semantics), for consistency.** Rejected: this would be a real security-posture change to already-shipped, production code, not a greenfield choice — anyone who configured a private CA for their broker today gets an implicit guarantee that *only* that CA is trusted for that connection; silently switching to additive on a version upgrade would mean a cert from an unrelated, valid public CA (e.g. attacker-controlled infrastructure with a Let's Encrypt cert on a hijacked DNS name) would suddenly be trusted where it wasn't before. A fixed broker bootstrap address also has no legitimate "might also need public-CA trust" scenario the way a dynamic HTTP-step URL does, so "replace" is arguably the *more* correct model there, not a legacy gap to close. If this is ever reconsidered, it needs its own design record (security posture change) and an explicit migration/changelog note — out of scope for this record, and not something implementing this decision should touch.
- **A single executor-wide flag** (extending `--allow-tls-skip-verify`'s model — one operator-supplied CA bundle trusted for every outbound HTTP call from that namespace's executor). Rejected: wrong scope, too broad. Different `Integration`s legitimately call different backends with different trust requirements (a public HTTPS API needing only the system root pool, alongside an internal service needing a private CA) — a single namespace-wide bundle would force every HTTP step to trust every configured private CA regardless of which backend it's actually calling, unnecessarily widening trust and running against the least-privilege posture the rest of this codebase follows (the SSRF blocklist, the executor's own minimal RBAC). Per-`Integration` scoping keeps added trust limited to exactly the steps that reference that specific backend.
- **`SecretKeyRef` for the CA bundle**, matching Kafka/AMQP/NATS's existing `caSecretRef` convention exactly for API consistency. Rejected per explicit owner decision: a CA bundle is public data (no private key material), and using `Secret` for it would be the same category error the fictional `kubezap.io/tls-ca-secret` annotation made (conflating public trust material with actual secrets). Chose correctness over sibling-type uniformity — noted as a real, accepted tradeoff below.
- **Passing the raw `ConfigMapKeyRef`/`SecretKeyRef` to the executor and letting it resolve the content itself** (fetch the ConfigMap/Secret directly from the API server). Rejected: violates the Constraints section's RBAC boundary — the executor is deliberately a low-privilege binary with zero secrets access; granting it `ConfigMap`/`Secret` read RBAC to support this one feature would expand its blast radius on compromise, undoing the entire reason a separate executor binary exists.
- **Caching resolved CA-bundle/client-cert material across reconciles or executor calls** (a persistent, Integration-keyed cache with its own invalidation). Rejected for v1: the resolution is already cheap (one `Get` call, identical cost to the existing per-reconcile `Integration`/auth-secret resolution `applyHTTPAuth` already performs on every reconcile that touches an HTTP step), and a cache adds real invalidation complexity (when does a resolved CA bundle go stale relative to a `ConfigMap` edit?) for no measured benefit. Revisit only if profiling under real load shows this resolution step is a bottleneck — nothing in STORY-015's benchmark data suggests HTTP-step dispatch is anywhere near that concern today.
- **A `ConfigMap`-watching reverse index** (an `internal/gateway/secretindex`-style informer + reverse index for CA-bundle `ConfigMap`s, to proactively reprocess dependents on rotation). Rejected: `internal/gateway/secretindex`'s docstring is explicit that it exists so long-lived gateway Deployments (which read a Trigger's secret once and hold a connection open) notice rotation without restarting. HTTP-step TLS resolution has no equivalent staleness problem — `applyHTTPIntegration` (and the `applyHTTPAuth` it already calls for secret-backed auth) re-fetches the referenced `Integration` fresh on every `FlowRun` reconcile that needs it; the only caching is the per-reconcile `Integration` cache (`ctx.Value(integrationCacheKey)`), which is scoped to a single reconcile pass and is discarded afterward. A rotated `ConfigMap` is therefore picked up automatically by the very next `FlowRun` step execution — no watcher needed, and adding one would be solving a problem this design doesn't have.

## 5. Tradeoffs

- **CPU cost per resolution.** Parsing PEM content and building an `x509.CertPool`/`tls.Certificate` happens on every `applyHTTPIntegration` call that resolves TLS config (bounded by the per-reconcile `Integration` cache, same as today's auth resolution) and again in `internal/executor/http/handler.go`'s `httpClient`, which builds a one-shot `*http.Transport` per call when `h.HTTPClient` is unset (the production path). This is strictly more work than today's zero-TLS-config path, though of the same order as parsing/applying an `Authorization` header already does — not expected to be measurable against STORY-015's ~5-10ms per-step dispatch baseline, but worth a real measurement once implemented rather than assuming.
- **API surface asymmetry.** `HttpIntegrationSpec`'s CA field will be `ConfigMap`-sourced while `KafkaTLSConfig`/`AmqpTLSConfig`/`NatsTLSConfig`'s `CASecretRef` are `Secret`-sourced — a deliberate inconsistency (see Rejected Alternatives) that a user skimming across Integration types has to notice and understand, rather than one uniform pattern everywhere.
- **PEM content flows through the RPC body as plaintext**, same as existing resolved `Authorization` header values do today. This is an accepted extension of the existing trust model (the controller→executor channel's own protection — mandatory `NetworkPolicy`, optional mTLS — already carries this class of sensitive data), not a new exposure, but it does mean request bodies grow by the size of the CA bundle (+ client cert, if configured) on every call to a TLS-configured backend, not just once at startup.
- **No rotation-latency guarantee beyond "next FlowRun."** Because there's no watcher, a `ConfigMap`/`Secret` update takes effect on the next `FlowRun` step execution that resolves it — fine for the common case, but means a namespace with no active Triggers for a given Integration won't visibly pick up a rotated CA until something actually fires again. Acceptable given the equivalent is already true for `HttpAuthSpec`'s existing secret-backed auth today.

## 6. Final Decision

Extend `HttpIntegrationSpec` (`api/v1alpha1/integration_types.go`) with an additive, `+optional` `TLS *HttpTLSSpec` field shaped `{CABundleConfigMapRef *corev1.ConfigMapKeySelector, ClientCertSecretRef *corev1.LocalObjectReference}` — `ConfigMap`-sourced CA bundle (owner-mandated, supports multiple concatenated PEM certificates in one key) and `Secret`-sourced client certificate (standard `tls.crt`/`tls.key` shape, matching the existing Kafka/AMQP/NATS `ClientCertSecretRef` convention). The controller resolves both in `internal/controller/flowrun_controller.go`'s `applyHTTPIntegration` (parallel to the existing `applyHTTPAuth` call, same function, same per-reconcile `Integration` cache), adding new inline PEM-content fields to `internal/executor/http/types.go`'s `ExecuteRequest` (`TLSCABundle`, `TLSClientCert`, `TLSClientKey` — resolved content, never a reference) so the RPC contract keeps working the way it already does for every other piece of resolved credential material, and the executor's RBAC stays exactly as minimal as it is today. `internal/executor/http/handler.go`'s `httpClient` gains the logic to build a `tls.Config` with `RootCAs`/`Certificates` set from those fields when present, alongside its existing `InsecureSkipVerify` handling — additive, no change to `tlsSkipVerify`'s behavior for steps that don't use the new fields. No watcher/reverse-index is needed (see Rejected Alternatives): TLS config is resolved fresh on every `FlowRun` reconcile, same as auth secrets already are, so rotation is handled by the existing resolution path with no new machinery. This is a purely additive change to `Integration`'s `v1alpha1` schema — no version bump required.
