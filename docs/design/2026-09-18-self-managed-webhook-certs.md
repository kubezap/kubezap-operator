# Self-Managed Webhook Admission Certs

> Status: Approved
> Related: `cmd/main.go`, `config/webhook/manifests.yaml`, `hack/gen-webhook-certs.sh`, `config/dev/manager_dev_patch.yaml`, `test/e2e/e2e_suite_test.go`, `benchmarks/execution-latency/scripts/setup.sh`

## 1. Problem Statement

`cmd/main.go` unconditionally starts a webhook TLS server (`webhook.NewServer`) and, when `--webhook-cert-path` is set, watches that directory for a cert/key pair via `certwatcher.CertWatcher` (`cmd/main.go:194-214`) to serve the three admission webhooks registered in `config/webhook/manifests.yaml` (`vflowrun.kb.io`, `vtrigger.kb.io`, `vwebhookgatewayconfig.kb.io`, all under one `ValidatingWebhookConfiguration` named `validating-webhook-configuration`).

Nothing in the repo actually provisions that cert or keeps the `ValidatingWebhookConfiguration`'s `caBundle` fields pointed at it — `config/certmanager` was never scaffolded, and there is no cert-manager `Certificate`/`Issuer` wired into `config/default`. Without a cert at `--webhook-cert-path`, the controller-manager crash-loops immediately on any `make deploy`.

The current stand-in is `hack/gen-webhook-certs.sh`: a manual `openssl` + `kubectl create secret` script, glued in via a separate `config/dev/manager_dev_patch.yaml` kustomize patch (adds the flag, a volume, and a volume mount), explicitly marked "NOT for production use." The same cert-provisioning steps are duplicated a second and third time in `test/e2e/e2e_suite_test.go:157-171` and `benchmarks/execution-latency/scripts/setup.sh:131-143`, each independently patching the Deployment via `kubectl patch`/JSON-patch. Three copies of the same bootstrapping logic, none of which is the production path, and none of which patches `caBundle` — webhook TLS verification only works today because kind/k3s's default admission-webhook client is configured to skip CA verification in these dev/test/benchmark setups, which is itself a gap this design should not perpetuate into whatever replaces it.

User impact: there is currently no supported way to run the operator's admission webhooks in production at all. Any real install (Helm, OLM/OperatorHub, raw manifests) either has to bring its own cert-manager install and wiring KubeZap doesn't provide, or ships with the webhooks silently broken.

## 2. Constraints

- No new hard dependency on cert-manager or any other cluster-installed component — the operator must be installable via Helm, raw manifests, or OLM/OperatorHub with no external cert provisioning step (per `docs/overview.md`'s supported install paths and OLM's own cert-injection assumptions).
- Must work identically across all four `WATCH_NAMESPACES` modes (OwnNamespace, SingleNamespace, MultiNamespace, AllNamespaces) and both Role/ClusterRole RBAC shapes.
- Must not weaken OpenShift restricted SCC compliance (non-root, no privilege escalation, read-only root FS where possible) — cert material is written to a Secret and to the existing `certwatcher`-watched directory (already an emptyDir/Secret-mounted volume in `config/dev`), not to arbitrary host paths.
- Must not require the leader-elected replica to be the only one capable of serving webhooks incorrectly during a rotation window — a rotation must not cause a availability gap in admission enforcement.
- Existing `--webhook-cert-path` / `--webhook-cert-name` / `--webhook-cert-key` flags and the `certwatcher.CertWatcher` wiring already in `cmd/main.go` are reused, not replaced — the gap being closed is *who writes the files that watcher reads*, not the watch/rotate mechanism itself, which already works.

## 3. Invariants

- At any point after the manager's leader-elected replica has completed one successful reconcile of its own cert, the `ValidatingWebhookConfiguration`'s `caBundle` for all three webhooks (`vflowrun.kb.io`, `vtrigger.kb.io`, `vwebhookgatewayconfig.kb.io`) matches the CA that signed the cert currently being served by `webhookCertWatcher`.
- A cert rotation (scheduled before expiry, or forced by Secret deletion) never produces a window where the served cert and the `caBundle` disagree — the `caBundle` is updated at the same time as, or before, the new cert is written to the watched directory, never after.
- Cert/key material is never logged, and the self-signed CA's private key never leaves the operator's own namespace (stored only in the Secret the manager itself creates/reads).
- If self-signed cert generation fails on startup (e.g. RBAC missing, API server unreachable), the manager fails fast with a clear error rather than starting the webhook server with no cert (which today manifests as an unexplained crash-loop from `certwatcher`).
- This mechanism is the *only* cert-provisioning path for the admission webhooks — dev, e2e, benchmark, and production all exercise the same code, so a bug caught in one is caught in all.

## 4. Rejected Alternatives

**Scaffold the standard kubebuilder cert-manager integration** (`config/certmanager/` self-signed `Issuer` + `Certificate`, `cert-manager.io/inject-ca-from` annotation on the `ValidatingWebhookConfiguration`, `[CERTMANAGER]` patches in `config/default/kustomization.yaml`). This is the well-trodden kubebuilder path and was the first option considered. Rejected because it turns cert-manager from "something users might already have for `WebhookGatewayConfig`'s TLS Secrets" (already an optional, documented convenience — see `docs/guides/webhook-security.md`) into a hard install-time dependency for the operator to even start correctly, for every install path (Helm, raw manifests, OLM/OperatorHub, every `WATCH_NAMESPACES` mode). That's a materially larger ask of every user than the operator's own admission webhooks warrant, especially since OLM already has its own independent cert-injection mechanism for CSV-declared webhooks — meaning cert-manager would only actually be load-bearing for the Helm/raw-manifest paths, adding an inconsistency between install methods rather than removing one.

**Leave `hack/gen-webhook-certs.sh` as the permanent dev/test/benchmark answer and just fix its stale doc reference.** Rejected: it does not solve production at all (explicitly "NOT for production use"), and its logic is already duplicated three times (the script itself, `test/e2e/e2e_suite_test.go`, `benchmarks/execution-latency/scripts/setup.sh`) with no `caBundle` patching in any of them — the drift risk and missing production path are the actual problem, not the stale citation alone.

## 5. Tradeoffs

- Adds new RBAC the manager didn't previously need: `get`/`create`/`update` on `secrets` (scoped to its own namespace only — not a new *scope* of Secret access, since the manager already handles Integration credential Secrets elsewhere, but a new *purpose*) and `get`/`update`/`patch` on `validatingwebhookconfigurations.admissionregistration.k8s.io` (cluster-scoped, since `ValidatingWebhookConfiguration` has no namespace — this is a new object *kind* of access the manager did not have before).
- The trust root is a self-signed CA generated and held entirely by the operator itself, with no external validation of that CA (same trust model as cert-manager's own self-signed `Issuer` would provide, and strictly better than today's no-`caBundle`-patching state, but weaker than an org-issued CA for environments that require one — those environments can still override `--webhook-cert-path` to point at externally-provisioned material, bypassing this mechanism entirely, same escape hatch cert-manager users would have today).
- A small amount of new long-lived code (cert generation, Secret read/write, CA bundle patch, rotation scheduling) that KubeZap now owns and must maintain, versus zero KubeZap code for the cert-manager alternative — offset by deleting three existing copies of dev/test/benchmark cert-provisioning logic and one shell script.
- Rotation logic runs in the leader-elected replica only (consistent with all other reconciliation in this operator); a non-leader replica's webhook server keeps serving its last-known-good cert from the watched directory during a rotation, per the existing `certwatcher` behavior — no new failover logic is introduced here.

## 6. Final Decision

Implement an in-process, self-managed cert lifecycle for the operator's own admission webhooks, following the pattern used by `open-policy-agent/cert-controller`: on startup (and periodically thereafter, leader-elected replica only), ensure a self-signed CA and a serving cert/key for `kubezap-webhook-service.<namespace>.svc` exist in a Secret in the operator's own namespace; write the serving cert/key to the directory already read by `cmd/main.go`'s `certwatcher.CertWatcher` (closing the gap in front of, not replacing, that existing watch/rotate wiring); and patch the CA's PEM bundle into all three `caBundle` fields on `validating-webhook-configuration`. This satisfies the no-new-cluster-dependency constraint that ruled out cert-manager, gives dev, e2e, benchmark, and production one identical code path (closing the actual bug class — missing `caBundle` patching — that all three ad hoc copies share today), and reuses rather than discards the `certwatcher` mechanism already in place. `hack/gen-webhook-certs.sh`, `config/dev/manager_dev_patch.yaml`, and the duplicated provisioning blocks in `test/e2e/e2e_suite_test.go` and `benchmarks/execution-latency/scripts/setup.sh` are all removed once the in-process mechanism lands and is verified across `make deploy`, `make test-e2e`, and a benchmark run.
