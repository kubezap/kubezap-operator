# Cluster-Scoped Namespace-Read RBAC for AllNamespaces-Mode Broker Gateways

> Status: Draft
> Date: 2026-09-19
> Related: `internal/gateway/{kafka,amqp,nats,webhook}/watcher.go`, `internal/controller/integration_controller.go`, `internal/controller/gateway_deployment.go`, `docs/design/allnamespaces-secrets-label-restriction.md`, `docs/design/allnamespaces-dynamic-secrets-rbac.md`, `planning/backlog/stories/STORY-053-canonical-rbac-completeness-audit.md`, `planning/backlog/stories/STORY-055-gateway-namespace-read-rbac.md`, `planning/backlog/stories/STORY-056-webhook-gateway-watch-namespaces-propagation.md`

## Problem

`docs/design/allnamespaces-secrets-label-restriction.md` (STORY-050) added a per-call check — `readSecretKey` in each gateway does `w.client.Get(ctx, types.NamespacedName{Name: namespace}, &corev1.Namespace{})` before resolving a Secret, refusing to proceed unless that namespace carries `kubezap.io/managed=true`. This is correct in design but was never actually reachable for three of the four gateway binaries: the Kafka/AMQP/NATS gateway pods each run under a namespace-scoped `Role`+`RoleBinding` (`kubezap-gateway`, reconciled per-namespace in `internal/controller/integration_controller.go`) bound to their own namespace-scoped `ServiceAccount`. A `RoleBinding` can only authorize requests for namespaced resources within that one namespace — it structurally cannot authorize a `Get` on a `Namespace` object, which is cluster-scoped, regardless of what verbs the bound `Role`'s rules list. So this check 403s for real, today, whenever `WATCH_NAMESPACES=*` and a Kafka/AMQP/NATS `Integration` has SASL/TLS secrets to resolve — the gateway can't complete the check at all, and loses its broker connection entirely (found by STORY-053's canonical RBAC audit, 2026-09-19).

The webhook gateway has the identical code path in `webhook/watcher.go`, but it's currently dead rather than broken: `desiredWebhookGatewayDeployment` never propagates `WATCH_NAMESPACES` into that container, so `allNamespacesMode` is always `false` there today (tracked separately as STORY-056, blocked on this decision).

## Constraints

- Must not grant any gateway ServiceAccount broader Secrets access than it already has — this design is about letting an existing, already-approved check actually execute, not expanding what it protects.
- The set of namespaces a gateway SA needs `Namespace`-read for is **not known at install time** — Integrations/Triggers (and therefore gateway Deployments) can appear in any namespace at runtime, so a statically-enumerated, install-time-only RBAC object cannot list every subject it will ever need.
- Must remain a no-op outside AllNamespaces mode: OwnNamespace/SingleNamespace/MultiNamespace installs use `Role` (not `ClusterRole`) by design (see `CLAUDE.md`) for OpenShift/OperatorHub certification reasons, and the underlying check itself is already a no-op there (STORY-050) — this design must not introduce any cluster-scoped object in those modes.
- Must not require a new dedicated reconciliation controller if a smaller mechanism suffices — `docs/design/allnamespaces-dynamic-secrets-rbac.md` (STORY-054) already rejected a comparable amount of new-controller complexity for a *higher-value* target (Secrets themselves) and was explicitly deferred; this problem is materially lower-stakes (`Namespace` objects carry labels/metadata only, no credential data) and should not default to the same weight of solution without justification.
- Kubernetes RBAC subject matching has no "this SA name in any namespace" wildcard — only an explicit `(namespace, name)` `ServiceAccount` subject, or a `system:serviceaccounts:<namespace>` group subject (which matches *every* SA in that namespace, not just the gateway's). Any design that grants this per-namespace, incrementally, has to pick one of these two subject shapes.
- OLM/OperatorHub: a new `ClusterRole`/`ClusterRoleBinding` in the bundle CSV must declare only the verb actually used (no `list`/`watch` speculatively added) to keep the permission set auditable and minimal, consistent with how `config/rbac/role.yaml` is already generated narrowly today.

## Rejected Alternatives

- **Per-namespace `Role`+`RoleBinding` granting `namespaces` access** — impossible, not just undesirable: `Namespace` is cluster-scoped, so no `RoleBinding` can ever authorize a `Get` on it, regardless of the bound `Role`'s rules. This is the exact bug being fixed, not a viable fix for it.
- **`system:serviceaccounts:<namespace>` group subject per namespace** (instead of naming the specific gateway SA) — rejected: grants `namespaces: get` to *every* ServiceAccount in that namespace, not just the gateway's own, which is broader than necessary for no benefit — the gateway's SA name is already a known constant (`kubezap-gateway`, or the webhook gateway's own deployment name), so naming it specifically costs nothing extra.
- **Full dynamic per-namespace RBAC controller** (mirroring STORY-054's rejected-then-deferred approach, generalized to also cover this) — rejected for this pass: STORY-054 already concluded a dedicated `Namespace`-watching controller is too much operational complexity to justify for the *Secrets* case; reusing that same weight of machinery for a lower-sensitivity, `get`-only, metadata-only read would be disproportionate. If STORY-054 is ever built, this design's ClusterRoleBinding-maintenance logic could be folded into it as one more thing that controller manages — but building a whole new controller *just* for this is not justified on its own.
- **Have the operator resolve the managed-label check and stamp a condition/annotation on the Integration/Trigger CR, so the gateway reads that instead of the Namespace object itself** — rejected for this pass: this trades a live, always-current check (the existing `Get`-per-call design, which can never be stale) for a cached one that goes stale until the operator's own watch/reconcile loop catches up to a namespace label flip. STORY-050 explicitly designed the per-call check to avoid exactly this kind of staleness window. It would also still require *some* mechanism for the operator to notice a `Namespace` label change and re-reconcile every Integration/Trigger in that namespace — meaningfully similar machinery to the rejected full-controller option above, for a worse (stale-by-default) result. Worth reconsidering only if the per-`Get` latency ever becomes a real problem, which nothing today suggests it is.
- **Drop the gateway-side check entirely, rely solely on the controller's own AllNamespaces checks (STORY-050)** — rejected: for Kafka/AMQP/NATS SASL/TLS credentials specifically, the gateway's own `readSecretKey` is the *only* enforcement point today; the controller does not independently resolve or gate these secrets anywhere else. Removing it would fully reopen the exact gap STORY-050 closed for three of the four gateway types, not just leave a smaller residual risk.

## Decision

Add one statically-generated `ClusterRole` (`kubezap-gateway-namespace-reader`, one rule: `apiGroups: [""], resources: ["namespaces"], verbs: ["get"]`), included in the Helm chart and raw manifests **only under the AllNamespaces install path** (the same conditional that already governs the operator's own ClusterRole-vs-Role choice) — this part needs no reconciliation, it's a fixed object like any other RBAC template.

Pair it with **two** dynamically-maintained `ClusterRoleBinding`s (one for the shared `kubezap-gateway` SA name used by the kafka/amqp/nats gateways, one for the webhook gateway's own SA name — see Constraints on why a specific-name subject is preferred over a namespace-group subject), each referencing the shared `ClusterRole` above. Maintenance is a small addition to the *existing* per-namespace gateway-reconcile functions (`reconcileKafkaGateway`, `reconcileAmqpGateway`, `reconcileNatsGateway` in `internal/controller/integration_controller.go`, and the webhook gateway's reconcile path once STORY-056 wires it up): whenever one of these runs for a namespace **and the operator is in AllNamespaces mode**, it ensures that namespace's gateway `ServiceAccount` is present in the appropriate shared `ClusterRoleBinding`'s `Subjects` list — an idempotent get-and-append, tolerating (and retrying on) a resource-version conflict from a concurrent reconcile touching the same shared object, the same way any other concurrent `controllerutil.CreateOrUpdate` caller would. Outside AllNamespaces mode, this logic is skipped entirely — no `ClusterRole`/`ClusterRoleBinding` is created or touched, matching STORY-050's mode-scoping.

This requires **no new controller**: it's a few extra lines appended to reconcile functions that already run per-namespace for exactly this purpose (standing up that namespace's gateway RBAC), not a new watch loop.

### Tradeoffs

- **Stale subject entries are accepted, not cleaned up.** If the last Integration/Trigger in a namespace is deleted and its gateway torn down, that namespace's SA subject entry is left in the shared `ClusterRoleBinding` indefinitely. This matches the *existing* precedent for the per-namespace `kubezap-gateway` Role/RoleBinding itself (also not owner-referenced or garbage-collected today, since it's shared across potentially multiple Integration types in that namespace and can't be tied to any one CR's lifecycle) and is low-risk here specifically because the granted resource is `Namespace` metadata (labels/annotations only) with no credential or workload data — an audit finding of "extra stale subjects on a get-only, non-sensitive ClusterRoleBinding" is a cosmetic cleanup item, not a security incident. Revisit only if this becomes a real audit concern.
- **Slightly broader-looking `kubectl auth can-i` surface for gateway SAs** — they gain a genuine cluster-scoped grant (unlike the operator's own Secrets restriction, which is application-level only per STORY-050, this one really is real RBAC, visible and correct under `kubectl auth can-i get namespaces --as=system:serviceaccount:<ns>:kubezap-gateway`). This is the intended, honest outcome, not a gap to document around.
- Two `ClusterRoleBinding` objects (not one) because the two gateway families use different SA names — slightly more to reconcile than a single shared binding, but keeps each binding's subject list meaningfully scoped to the SA it's actually for, and avoids a spurious dependency between the kafka/amqp/nats reconcile path and the webhook one.
