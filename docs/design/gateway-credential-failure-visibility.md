# Surface Gateway Credential-Resolution Failures as a Kubernetes-Visible Signal

> Status: Draft
> Related: `internal/gateway/{kafka,amqp,nats}/watcher.go`, `api/v1alpha1/trigger_types.go`, `internal/controller/trigger_controller.go`, `internal/controller/integration_controller.go`

## 1. Problem Statement

Confirmed via code (this record's investigation, not assumed): when the kafka/amqp/nats gateway watchers' `reconcileTrigger` fails to resolve an Integration's credentials (missing/invalid Secret, malformed spec, any resolution error), the failure is logged (`w.log.Error(...)`) and nothing else. Tracing `TriggerStatus` (`api/v1alpha1/trigger_types.go`) and every write site for it (`grep` across `internal/controller/`) found exactly two writers — `cron_scheduler.go` and one `"Accepted"` write in `trigger_controller.go` — both **inside the controller process**, which already owns `triggers/status` RBAC. No gateway process writes to `Trigger` at all today: the kafka gateway's Role (`internal/controller/integration_controller.go`) grants only `get/list/watch` on `triggers` and `create` on `flowruns` — no write verb on `triggers` or `triggers/status` whatsoever, for any of the three broker gateways. So a credential-resolution failure is structurally invisible outside gateway pod logs: no Condition, no Event, nothing `kubectl get`/`describe trigger` surfaces.

`TriggerStatus.LastResult`/`LastError` look like a ready-made fit at first glance but aren't: their doc comments ("outcome of the last trigger **attempt**") and only real writer (`cron_scheduler.go`, on an actual firing) show they mean "did an inbound event get processed," not "is the subscription even alive." Overloading them for a credential-resolution failure — which happens *before* any attempt, when the watcher can't even establish its subscription — would misrepresent state an operator reads literally (`LastResult: Failed` implies an event fired and processing failed, not "never even connected").

Also confirmed: **Kubernetes Events aren't used anywhere in this codebase today** (`grep` for `EventRecorder`/`record.Event(` across `internal/`/`cmd/` returns nothing) — any Event-based mechanism here is new plumbing, not an extension of an existing pattern, unlike this session's other gateway-informer stories.

## 2. Constraints

- No CRD schema change to `Trigger` itself — `TriggerStatus.Conditions []metav1.Condition` already exists, unpopulated; reuse it rather than adding fields.
- Minimize new RBAC on the three broker gateway Roles specifically — these already run with intentionally narrow, recently-audited grants (a prior RBAC-completeness audit found 0 gaps; a recent Integration-informer addition justified its new grant individually rather than defaulting to broad access). A direct `triggers/status: patch` (or worse, `triggers: update/patch` for an annotation-based signal, since gateways currently have no write verb on `triggers` at all) would be a materially larger widening than anything granted recently.
- Must not conflate this with webhook gateway auth failures — a different failure class (see Rejected Alternatives) already covered by structured access logs + Prometheus metrics (`docs/guides/observability.md`).
- Must not introduce a high-frequency signal — whatever mechanism is chosen must fit a low-frequency, persists-until-fixed failure (credential resolution breaks once, stays broken until the operator fixes the Secret/Integration), not a per-event signal.
- Namespace-scoped only — no ClusterRole, consistent with every other RBAC grant in this project (`docs/design/namespace-scoped-watch-modes-only.md`).

## 3. Invariants

- A persisting credential-resolution failure for a Trigger is visible via `kubectl describe trigger <name>` within one gateway reconcile cycle of occurring.
- A persisting credential-resolution failure eventually produces a real `status.conditions` entry on the `Trigger` (queryable via `kubectl get`/API, not just human-readable `describe` output) within a bounded number of controller reconcile cycles — not left as an Event-only signal.
- No broker gateway ServiceAccount gains write access to the `Trigger` object or its `status` subresource — the mechanism must not require it.
- Once the underlying credential/Integration is fixed and a subsequent `reconcileTrigger` succeeds, the Condition clears (transitions to `True`/resolved) — this isn't a one-shot "something went wrong once" marker.
- Webhook gateway auth failures are explicitly out of scope for this mechanism (see Rejected Alternatives) — this applies to the three broker watchers' credential-resolution failures only.

## 4. Rejected Alternatives

**Grant the gateway processes RBAC to patch their own Trigger's `status.conditions` directly.** The simplest mechanism, and the story's own first candidate. Rejected as the primary mechanism: it's the largest RBAC widening of the three candidates, applied identically across three separate gateway ServiceAccounts (kafka, amqp, nats), for pods with more externally-influenced attack surface than the controller (they process broker-delivered payloads). It also duplicates the controller's existing ownership of `Trigger` status with a second, gateway-side write path — two writers of the same subresource is exactly the kind of thing that produces races/stale-overwrite bugs later (a gateway's stale-informer view patching status.conditions after the controller already changed something else). Not worth it when a lower-privilege alternative delivers the same operator-visible outcome.

**Route the failure back through the controller via an annotation or a direct field on the Trigger.** Considered as "Option B" in the original story. Investigation found this is actually *worse* on the RBAC axis than directly patching status: gateways currently have **zero** write verbs on `triggers` at all (not even `update`/`patch` on the base resource), so an annotation-based signal needs a *new*, broader grant (write access to the whole object, which could then also rewrite `spec` fields) — larger blast radius than a scoped `status` patch would have been, let alone the Event-based mechanism actually chosen below.

**Emit a Kubernetes `Event` and stop there (no controller-side Condition).** This is the story's third candidate, taken alone. Rejected as the *complete* solution, though it's half of the chosen one: Events aren't part of `Trigger`'s `status`, so they don't show up in `kubectl get trigger -o wide` printcolumns or anything that queries object state via the API rather than `describe`/event-stream tooling — a real gap for future automation (alerting, status aggregation) that expects Conditions, the standard Kubernetes idiom for "current state of this object." Kept as the low-privilege *signal* half of the mechanism, not the whole answer.

**Also cover webhook gateway auth failures with the same mechanism.** Rejected: webhook auth failures are a fundamentally different failure class — per-request (a bad signature on one incoming call), potentially high-frequency (every malicious or misconfigured caller), and already covered by structured access logs plus Prometheus metrics (`docs/guides/observability.md`). Kubernetes Events are not designed for per-request-rate signals; emitting one per rejected webhook request would spam the Event stream and defeats the low-frequency assumption this design relies on. Broker credential-resolution failure is a *state*-level failure (breaks once, stays broken until fixed) — the right shape for this mechanism; webhook auth failure is not.

## 5. Tradeoffs

- **Two-hop latency to a real Condition**: the Event is visible immediately (`describe`), but the Condition only appears after the controller's own Event-watching logic picks it up — a new informer/reconcile path, not instant. An operator relying purely on `kubectl get trigger` (not `describe`) sees a short lag versus a hypothetical direct-patch design.
- **New plumbing, not an extension of an existing pattern**: this project has no `EventRecorder` usage anywhere today. Both sides (gateway emission, controller consumption) are new code, not a small addition to something already working — genuinely more implementation surface than the "just widen an existing informer" pattern this session's other gateway stories used.
- **Kubernetes Event TTL**: a single persisting failure naturally coalesces into one Event with a bumped `count`/`lastTimestamp` (client-go's standard `EventRecorder` dedup behavior) rather than spamming new entries, but if the underlying `--event-ttl` (cluster-operator-controlled, not KubeZap's) expires it before the controller's Condition-sync catches up, the Event-based visibility gap could reopen briefly — mitigated by the Condition being the durable, non-expiring record once synced.

## 6. Final Decision

Two-part mechanism, chosen specifically to keep broker gateway RBAC as narrow as every other grant made this session: (1) the kafka/amqp/nats watchers gain a `record.EventRecorder` and emit a `Warning`-type `Event` (reason e.g. `CredentialResolutionFailed`) referencing the Trigger whenever `reconcileTrigger`'s credential-resolution step fails — requiring only new `events: create` RBAC on the three broker gateway Roles, no write access to `Trigger` or its `status` subresource at all. (2) The controller (which already owns `triggers/status`) adds a new `Event` informer, filtered to `involvedObject.kind=Trigger` with this reason, and translates a persisting one into a real `status.conditions` entry (clearing it on the next successful `reconcileTrigger`) — reusing the controller's existing `apimeta.SetStatusCondition` pattern already used for `Flow`/`Integration`/`WebhookGatewayConfig`/`FlowRun`. This delivers both immediate `describe`-visible signal and eventual API-queryable state without a second writer touching `Trigger` status, and without granting any broker gateway anything beyond the narrowest verb (`events: create`) the underlying problem actually requires. Explicitly scoped to the three broker watchers' credential-resolution failures — webhook gateway auth failures stay on their existing access-log/metrics path, a different failure class (high-frequency, already covered) that this mechanism isn't shaped for.
