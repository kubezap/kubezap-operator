# Close the SSRF DNS-rebinding gap at the HTTP transport level

> Status: Draft
> Related: `internal/executor/http/ssrf.go`, `internal/executor/http/handler.go`, `docs/design/2026-09-11-executor-egress-networkpolicy.md`, `STORY-031`

## 1. Problem Statement

The HTTP executor's SSRF defense (`checkSSRF` in `internal/executor/http/ssrf.go`) resolves the target hostname, validates every resolved address against the blocked-CIDR list, and — if that passes — hands the original URL to a standard `http.Client`. The `http.Transport` then performs its *own*, independent DNS resolution when it actually dials the connection. An attacker who controls the target hostname's DNS (a very short TTL record) can return a safe address for the validation lookup and a blocked/internal address for the connection lookup a moment later — classic DNS rebinding. This defeats the software check entirely; it never blocks the address that's actually connected to.

Today this gap is partially covered by a NetworkPolicy egress rule (`docs/design/2026-09-11-executor-egress-networkpolicy.md`) that blocks the same CIDR ranges at the network layer — but only on a CNI that enforces NetworkPolicy egress (Calico, Cilium, most managed-Kubernetes defaults). On a non-enforcing CNI (plain Flannel — notably **the default CNI on k3s, this project's own documented local/dev/test platform**), the software check is the only defense, and rebinding defeats it completely.

This is not purely a "trusted Flow author" risk either: HTTP step URLs support `$(trigger.body.<field>)` interpolation (`docs/api/flow.md`), so a Flow that builds part of its request URL from webhook payload data (a "callback URL" pattern) lets an unauthenticated external caller influence the target hostname. Combined with a non-enforcing CNI, that's a remote, unauthenticated path to internal-network/metadata-endpoint access.

## 2. Constraints

- No change to the executor's request/response contract (`ExecuteRequest`/`ExecuteResponse`) — this is an internal transport-construction change only, not an API change.
- No new external dependency (no forward proxy, no dedicated resolver sidecar) — must stay within `net`/`net/http` stdlib, consistent with the executor's design as a minimal, low-privilege pod (`docs/architecture.md`: "Minimal RBAC — no secrets, no RBAC management").
- Must not regress TLS certificate hostname verification: certificate validation must still check the original request hostname, never the pinned connection IP.
- Must not change the `--blocked-cidrs` flag or `BlockedCIDRs`/`AllowClusterInternal` handler fields' documented semantics.
- Must preserve the `AllowClusterInternal` dev/test bypass's existing scoping: it may only skip validation for `.svc.cluster.local` hostnames, never for IP literals or other hostnames (see the existing doc comment in `ssrf.go`).
- Must preserve the existing per-request `http.Transport` construction (`handler.go`'s `httpClient` builds a fresh `Transport` per `/execute` call) — no shared connection-pool redesign.

## 3. Invariants

- Every TCP connection the executor's outbound client establishes for a given request — the initial connection and any redirect-triggered connection to a different host — connects only to an IP address that was validated against the blocked-CIDR/cluster-internal rules using the *same* DNS resolution that produced that connection. There is no window between "resolve and validate" and "resolve and connect" where a second, different lookup can occur.
- TLS certificate verification for an HTTPS target always validates against the original request hostname, never the pinned IP address used for the socket connection.
- A hostname that resolves to any address in a blocked range is rejected in its entirety (fail-closed), even if it also resolves to a non-blocked address — this matches `checkSSRF`'s existing documented behavior and must not silently loosen.
- `.svc.cluster.local` targets remain subject to `AllowClusterInternal`'s existing scoping: bypass applies only to that hostname suffix, never to IP literals or other hostnames, regardless of this change.

## 4. Rejected Alternatives

**Document the CNI-enforcement dependency more prominently and defer implementation.** This was the default option this record was required to weigh seriously (per `STORY-031`'s own notes) given the NetworkPolicy mitigation already covers the common case of an enforcing CNI, at meaningfully lower cost than a transport rewrite. Rejected because the "common case" assumption doesn't hold for this project specifically: k3s — the platform `CLAUDE.md` and `docs/overview.md` document as this project's own supported local/dev/test target — ships Flannel by default, which does not enforce NetworkPolicy egress. Combined with `$(trigger.body.*)` URL interpolation making the attacker-controlled-hostname scenario reachable by an unauthenticated webhook caller (not just a trusted Flow author with RBAC access), deferring leaves a plausible, real-world exploitable path with only a docs-level warning as mitigation. The actual implementation also turned out cheaper than the story's own estimate assumed once the executor's existing per-request `Transport` construction was examined (see Tradeoffs) — the cost side of this tradeoff was overstated when the story was groomed.

**`http.Client.CheckRedirect`-only revalidation, leaving the transport's own connection-time resolution untouched for the initial request.** Would close the redirect-hop variant of the gap but not the primary reported one: the transport still performs its own unvalidated resolution when dialing the *first* connection after our pre-flight `checkSSRF` passes, so the core rebinding window remains open. Rejected as incomplete.

**Route executor egress through a forward proxy or dedicated DNS-enforcing resolver (e.g. an Envoy/Squid sidecar with an allowlist).** Would close the gap independent of application code, but adds a new deployable component and operational dependency across every install path (raw manifests, Helm, OLM all need it configured identically), conflicting with the executor's documented design as a minimal, low-RBAC pod. Also strictly more operational surface than an in-process `DialContext` change achieves for the same security property. Rejected as disproportionate.

**Resolve all addresses and fall back to the next one if the first is unreachable or blocked (Happy-Eyeballs-style multi-address dial).** Considered, not chosen. Adds real retry/fallback state to the dial path for a reliability benefit (dual-stack fallback when the preferred address is down) that isn't required by the security fix itself, and changes the existing fail-closed "any blocked address rejects the whole hostname" semantics into something more permissive and harder to reason about. See Tradeoffs for the reliability cost of not doing this.

## 5. Tradeoffs

- **Loses standard-library Happy-Eyeballs-style fallback for dual-stack hosts.** If a hostname's first resolved address is valid (not blocked) but unreachable for a non-security reason (routing issue, that specific address down), the request now fails outright instead of the stdlib transport silently retrying a sibling address. Accepted: Flow HTTP step targets are typically single-A-record public APIs/webhooks, and the executor already forgoes cross-request connection pooling by design, so this isn't a new category of fragility relative to the current baseline.
- **Net DNS lookup count is roughly unchanged, but enforcement coverage increases.** Previously: one validated lookup (pre-flight) + one unvalidated lookup (transport dial) per connection — 2 lookups, only the first enforced. Now: exactly one validated lookup per connection (the pre-flight's DNS-resolution step is removed to avoid a redundant, still-TOCTOU-vulnerable second lookup; only the structural checks — empty hostname, `.svc.cluster.local` handling — stay pre-flight). On a multi-hop redirect chain to N distinct hosts, each hop gets its own validated lookup, where before only the original hostname was checked at all.
- **More logic in the hot dial path.** A custom `DialContext` replacing a plain `net.Dialer.DialContext` is more code for a future contributor to understand correctly before touching, raising the risk that a later "simplification" silently reintroduces the gap. Mitigated with an explicit doc comment on the function stating why it exists, plus a dedicated test using a fake/injectable resolver that returns different addresses across calls to assert the rebinding scenario is actually blocked (not just that the happy path still works) — a regression here fails CI, not just code review.

## 6. Final Decision

Implement the transport-level fix now rather than deferring. Add a custom `DialContext` to the executor's per-request `http.Transport` that performs hostname resolution and blocked-CIDR/cluster-internal validation (the resolution logic currently in `checkSSRF`, refactored to also return the validated address) and dials that specific validated address directly — for *every* connection the transport establishes, including ones triggered by a redirect to a different host, since each such connection goes through this same `DialContext`. This closes the TOCTOU window structurally rather than narrowing it, independent of NetworkPolicy/CNI enforcement. `ServeExecute`'s existing pre-flight checks (empty hostname, `.svc.cluster.local` + `AllowClusterInternal` handling) stay in place for fast, clear errors before any network I/O; the DNS-resolution-and-CIDR-check step itself moves to be dial-time-only so there's exactly one, enforced resolution per connection instead of two, only one of which was ever checked. TLS certificate hostname verification is unaffected — Go's `http.Transport` derives `ServerName` from the original request host independent of what `DialContext` returns, so verification continues to check the hostname the user configured, not the pinned IP.
