## Prioritization rationale

Items are ordered to minimize rework:

1. **Research first** — find breaking bugs and interference issues before writing tests or building features on top of them. Tests written against broken behavior must be rewritten after the fix.
2. **Bug fixes before validation that exercises the same code** — running a manual E2E pass over broken behavior produces misleading results. Fix known bugs first.
3. **Prerequisites before dependents** — if item B requires a type, API, or behavior introduced by item A, A must come first.
4. **Tests before new feature development in the same area** — once an area has confirmed-correct behavior, test it before adding more features on top.
5. **P0 security fixes before architectural refactors in the same code area** — a security vulnerability should not be blocked waiting for a large refactor.
6. **Public readiness (§16) gates OperatorHub submission (§1)** — all P0 items in §16 must be complete before the OperatorHub submission PR is opened. P1 items should be resolved first; P2 items are nice-to-have.
7. **§18 P1 items before §16 P1 validation pass** — the VALIDATION item is a full E2E system exercise. Running it before §18 P1 items (status reporting bug, security checklist) gives incomplete results and may need to be re-run.
8. **§22 (automated e2e) before §19 (manual e2e)** — automated tests must pass before manual validation is meaningful. Fix e2e suite health first.
9. **§20/§21 research (code review, doc review) before §19 manual E2E** — code review may surface bugs that invalidate manual validation results; doc review may expose example incorrectness. Run both before the full manual pass.
10. **§23/§24 P0 fixes before §19 manual E2E** — the P0 findings from §20/§21 (code bugs, doc-reality mismatches) must be resolved before manual validation. E2E over broken or incorrectly documented behavior produces misleading results and may need to be re-run.

## 29. Secret Rotation Detection Gap — 2026-09-10

> Raised by owner: does the operator detect a Secret rotated externally (e.g. by External Secrets Operator) without the referencing Trigger/Integration being touched?

- [x] **BUG (fixed 2026-09-11)** — Webhook Trigger auth secrets (HMAC/bearer/basic/apiKey/header-equals — `internal/gateway/webhook/watcher.go`) and Kafka/AMQP/NATS broker credentials (SASL/TLS — `internal/gateway/{kafka,amqp,nats}/watcher.go`) were read once when the gateway processed a Trigger/Integration add-or-update event, then cached in memory in the route/subscription entry for its lifetime, with no watch on `Secret` objects anywhere. Design record: **`docs/design/2026-09-11-secret-rotation-watches.md`**. **Also found while researching this fix, more severe**: the kafka/amqp/nats gateways' shared `kubezap-gateway` Role had **no `secrets` permission of any kind** — not even `get` — so `readSecretKey`'s live API call must already have been failing with `Forbidden` in any real cluster with SASL/TLS actually configured; this went unnoticed because every live E2E validation of `kafka-enrichment`/`dlq-handler` used a plaintext, unauthenticated Strimzi cluster. **Fix**: added a `corev1.Secret` informer to all four watchers (same `crcache.Cache` each already owns for its `Trigger` informer) with a new, small shared `internal/gateway/secretindex` package providing a thread-safe reverse index (Secret key → dependent Trigger keys), rebuilt every time a Trigger is reconciled so stale references clean up automatically. On a Secret change, every affected Trigger is reprocessed through the exact same code path a real Trigger spec change takes (`handleTrigger` for webhook, `reconcileTrigger` for kafka/amqp/nats) using each Trigger's most recently seen object — no extra API call. For kafka/amqp/nats, added a `credentialFingerprint` (SHA-256 of the resolved SASL/TLS/username material) to each `subscription`, since the existing "topic/consumerGroup/integrationName unchanged, skip restart" fast path would otherwise silently swallow a credential-only rotation. Fixed the prerequisite RBAC gap in the same change: `desiredWebhookGatewayRole` upgraded from `secrets: get` to `get/list/watch`; `desiredKafkaGatewayRole`/`desiredAmqpGatewayRole`/`desiredNatsGatewayRole` (previously no secrets rule at all) all gained `secrets: get/list/watch`. New tests: `internal/gateway/secretindex` (6 unit tests, 100% coverage), plus per-watcher tests for credential fingerprinting, index population, secret-rotation reprocessing, and delete cleanup across all 4 gateway packages, plus one `internal/controller` test asserting the RBAC fix. `go build`/`go vet`/`make test` all pass; no CRD/RBAC manifest drift (these Role rule sets are plain Go structs, not `+kubebuilder:rbac`-marker-derived).
- [x] **DECIDED, no code change (2026-09-11)** — Related and lower-severity, a different code path from the gateway watchers fixed above: the `type: publish` Kafka producer cache (`internal/controller/flowrun_controller.go`'s `kafkaProducers`, used when a Flow step publishes *to* Kafka) doesn't notice a SASL/TLS secret rotation — only `kafkaProducerIdleTTL` (10 minutes) eventually forces a reconnect. - [x] **CONFIRMED WORKING (no gap)** — Outbound HTTP step auth (Bearer/Basic/APIKey/SecretURL — `internal/controller/flowrun_controller.go` `fetchSecretValue`) is fetched fresh on every step execution, not cached across FlowRuns. ## 30. RBAC Markers Silently Dropped (misplaced package-scoped markers) — 2026-09-10

> Discovered while investigating §26's RBAC drift item. A KubeZap source bug (marker placement), not an environment or controller-gen fault — the initial diagnosis in this section was wrong and has been corrected below. Dangerous because it fails **silently**: `make manifests` exits 0 and simply omits the rules.

- [x] **BUG (root-caused and fixed 2026-09-10)** — `+kubebuilder:rbac` is a **package-scoped** marker. In `executor_reconciler.go` the four RBAC markers were written inside the doc comment attached directly to `type ExecutorReconciler struct` (prose, then `//`, then the markers, with no blank line before the type). controller-gen only collects package-scoped markers from **free-floating** comment groups — when they appear in a declaration's doc comment it **silently ignores them**, with no warning and no error. Result: `networking.k8s.io/networkpolicies` and the `secrets` write verbs never reached `config/rbac/role.yaml`, so the operator shipped without permissions its own code required — the cause of the recurring `Failed to reconcile executor NetworkPolicy` errors in §26. **Fix**: moved the marker block above the doc comment, separated by a blank line (matching the pattern already used correctly by the other seven marker-bearing files), then re-ran `make manifests` — the rules now generate correctly, and the manual patch previously applied to `role.yaml` was removed as no longer needed. Audited every other `+kubebuilder:rbac` block in the repo: all seven others were already correctly free-floating; `executor_reconciler.go` was the only one affected. Added a guard note to `CLAUDE.md` Coding Conventions, since the failure mode is completely silent.

  <details><summary>Why this took so long to spot (kept for future debugging reference)</summary>

  The silence sent the earlier investigation down a wrong path — it looked like an environment/tooling fault rather than a source bug, because: adding a canary marker to a brand-new file also produced nothing (that canary was itself attached to a `var` declaration, so it hit the exact same rule); a deliberately broken Go file produced no error either (controller-gen tolerates it); and upgrading controller-gen v0.18.0 → v0.22.0 changed nothing (correct — the behavior is by design, not a version bug). `GOCACHE`, path style, `replace` directives, `vendor/`, `GOFLAGS`/`GOWORK` were all ruled out and all were red herrings. The decisive test was comparing the comment-group *structure* of a working marker block against the broken one, not the marker text (whose bytes were byte-for-byte clean ASCII).

## 35. Interpolation Security Audit — 2026-09-11

> Targeted review of `substituteVars`/`substituteVarsWithSecrets` (the `$(...)` placeholder resolver used for every step field), following the pattern in `docs/guides/code-review-strategy.md` of naming one concern rather than an open-ended scan: the trust boundary where attacker-controlled trigger data (an unauthenticated webhook body or header) flows into placeholder resolution. Design record: `docs/design/2026-09-11-single-pass-interpolation.md`.

### P0 — Fix before public release

- [x] **BUG, security — remote DoS (fixed 2026-09-11)** — `substituteVars`'s `$(trigger.body.<field>)` and `$(trigger.headers.<name>)` resolution loops scanned-and-`ReplaceAll`'d against their own output: the loop condition (`strings.Index(s, prefix)`) was re-evaluated against `s` *after* each replacement, so a resolved value containing the same placeholder text was found and "resolved" again, forever. Confirmed live: a webhook body `{"a": "$(trigger.body.a)"}` fed into a Flow that interpolates `$(trigger.body.a)` hung the reconcile goroutine at 100% CPU indefinitely (same for a request header echoing its own `$(trigger.headers.*)` placeholder). With `MaxConcurrentReconciles` (default 10), ten such unauthenticated requests exhaust the controller's entire reconcile capacity. Root cause and fix shared with the next finding.
- [x] **BUG, security — secret exfiltration (fixed 2026-09-11)** — `substituteVarsWithSecrets` resolved non-secret placeholders first, then scanned the *result* for `$(secrets.<name>.<key>)`. Any attacker-controlled string (a body field, header, or an upstream step/API result) that happened to land in a template alongside one legitimate `$(secrets.*)` reference (a common shape: an auth token plus interpolated user data in the same request) could inject literal `$(secrets.<any-name>.<any-key>)` text and have it resolved and sent onward — reading **any** secret in the namespace, not just ones the Flow author referenced.

## 37. Webhook Attack Surface Hardening — 2026-09-11

> Adversarial review of the webhook trigger ingestion path, framed as: an external attacker who knows the target runs KubeZap and exposes webhook-triggered Flows, with no access to the target's actual Trigger/Flow configs. 5 findings. Owner asked to first weigh each against infra-layer mitigation (WAF, security groups, managed load balancers) before defaulting to a code fix — see decisions below. Design records: `docs/design/2026-09-11-webhook-gateway-trust-boundary.md`, `docs/design/2026-09-11-executor-egress-networkpolicy.md`.

### P0 — Fixed in code

- [x] **BUG, security — `ipAllowlist` webhook auth trivially bypassable (fixed 2026-09-11)** — `realClientIP` (`internal/gateway/webhook/accesslog.go`) unconditionally trusted `X-Forwarded-For`/`X-Real-IP` from the request itself, with no concept of a trusted proxy; `authenticateRequest`'s `ipAllowlist` case called it directly to decide access. Any caller reaching the gateway directly — the entire point of a webhook — could send `X-Forwarded-For: <any-allowed-ip>` and be treated as that IP; even behind a proxy that correctly appends the real IP, the code took the *first* comma-separated entry, so a client-injected fake entry still won. Zero existing test coverage for `ipAllowlist` or `realClientIP` (confirmed by grep) before this fix. **Decided: fix in code, not delegate to infra** — this is the product's own advertised auth feature; a WAF/security-group IP restriction in front is a fine *redundant* layer but doesn't repair a customer relying on KubeZap's own allowlist, and most reverse proxies append to `X-Forwarded-For` rather than overwrite it by default, so even a "trusted" proxy in front doesn't neutralize the bug on its own. Fixed: `realClientIP` now takes `trustedProxies []*net.IPNet` and never consults either header unless the immediate TCP peer (`r.RemoteAddr`) is itself in that set — when empty (the default), the headers are never trusted at all; when set, the *right-most* `X-Forwarded-For` entry is used (the one the trusted hop itself observed, unspoofable by anything earlier in the chain). New `--trusted-proxy-cidrs` flag on `webhook-gateway`. Threaded into both `authenticateRequest` (security-relevant) and `AccessLogMiddleware`/the per-request access log (consistency). 7 new tests covering the previously-uncovered `ipAllowlist` path directly, including a spoofed-header-rejected-by-default regression test and a legitimate-trusted-proxy-honored test.
- [x] **BUG, security — SSRF blocklist has a DNS-rebinding TOCTOU gap; primary fix delegated to infra (fixed 2026-09-11)** — `checkSSRF` (`internal/executor/http/ssrf.go`, duplicated in `internal/controller/ssrf.go`) resolves a step's target hostname, validates *those* addresses, then returns; the actual request re-resolves the same hostname independently via the stdlib transport. A hostname with attacker-controlled DNS (realistic whenever a Flow interpolates external data into a step URL) can return a safe address for validation and a blocked one (e.g. `169.254.169.254`) for the real connection moments later via a low TTL — the standard DNS-rebinding SSRF bypass, unfixable by making the CIDR list more complete. **Decided: primary fix at the network layer, not the software check** — NetworkPolicy filters the actual destination IP of the real packet, which DNS trickery cannot fool the way it fools a resolve-then-reconnect app-level check; fixing this properly in the HTTP transport (pin the validated IP, redial for redirects, preserve SNI/Host) is meaningfully more complex and regression-prone for a problem the network layer is structurally immune to. Found in the process: the project already ships a *manual* reference NetworkPolicy (`config/network-policy/http-executor-ingress.yaml`) modeling exactly this defense, applied via a documented `kubectl apply -f config/network-policy/` step — but (a) it's missing `169.254.0.0/16` (link-local/cloud-metadata, the single most commonly exploited SSRF target) from its exception list, and (b) the NetworkPolicy the operator actually auto-creates for every managed namespace (`reconcileExecutorNetworkPolicy`) only restricts Ingress, no Egress at all. Fixed: extended `reconcileExecutorNetworkPolicy` to add an Egress rule blocking the same ranges as `defaultSSRFBlockedCIDRs` (now on by default, no manual step required), fixed the missing exception in the manual reference file, and cross-referenced the SSRF and NetworkPolicy sections of `docs/guides/security-checklist.md` (previously two unconnected checklist items) with an explicit caveat that this requires a `NetworkPolicy`-enforcing CNI (Calico/Cilium; not plain Flannel) and a cloud-security-group fallback for clusters where it doesn't. New test extends the existing `executor_reconciler_test.go` NetworkPolicy assertions to cover the Egress rule; verified the test actually exercises the new code by deliberately breaking one assertion and confirming it failed, then reverting.

### P1 — Fixed in code

- [x] **BUG (fixed 2026-09-11)** — `cmd/webhook-gateway/main.go`'s public `http.Server` had no `ReadHeaderTimeout`/`ReadTimeout`/`WriteTimeout`/`IdleTimeout` (Slowloris-style connection exhaustion). `http-executor` — an *internal*, far less exposed service — already sets all four; the actually-public-facing binary was the one missing them. **Decided: fix in code regardless of what's in front** — a managed load balancer often absorbs this, but the fix is ~5 lines with zero behavioral change for legitimate traffic, so there's no reason to make it "depends on your deployment." Added `ReadHeaderTimeout: 10s`, `ReadTimeout: 30s`, `WriteTimeout: 30s`, `IdleTimeout: 120s`, mirroring `http-executor`'s existing values.

### P1 — Documented as an operator/infra responsibility, not fixed in code

- [x] **GAP (documented 2026-09-11)** — `Trigger.spec.webhook.cooldown` is opt-in per-Trigger; an unconfigured Trigger accepts unlimited FlowRun creation as fast as the 4MB body-read allows, each one an etcd object plus a reconcile plus potentially an outbound call the Flow makes (amplification, not just gateway load). **Decided: document as a required operator checklist item, do not hardcode a default rate limit** — a baked-in default risks breaking legitimate high-throughput Triggers the project can't anticipate, and real volumetric flood protection belongs upstream of the cluster (WAF rate-based rules, ingress `limit-rps` annotations, API Gateway throttling), where it can act before a request costs the gateway a TCP/TLS handshake at all — something no in-process limiter can do regardless of how it's tuned. ### P2 — Fixed in code (found more severe than initially scoped, during the fix)

- [x] **BUG (fixed 2026-09-11, scope corrected during implementation)** — the hardcoded 4096-byte cap on stored `TriggerData.Body` (independent of, and much smaller than, the 4MB read limit) was undocumented and unconfigurable. A transport-level fix (pin the validated IP, redial per-redirect, preserve SNI/Host) would close the gap independent of CNI, at meaningfully higher implementation complexity/risk — explicitly not rejected permanently in that design record, just deferred in favor of the lower-risk NetworkPolicy fix. Revisit if a deployment on a non-enforcing CNI needs this closed.

Noted as a revisit-if-drift-becomes-a-problem tradeoff in `docs/design/2026-09-11-executor-egress-networkpolicy.md` (e.g. generate the NetworkPolicy except-list from the Go slice at build time).
