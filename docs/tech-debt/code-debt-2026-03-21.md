## BUG — Flow validation rejects `type: wait` actions

**Location:** `internal/controller/flow_controller.go` — `validateFlowSpec()` switch statement (lines ~107–129)

**Description:** The switch only handles `"http"`, `"transform"`, and `"publish"`. The `"wait"` action type is valid in the CRD schema (`api/v1alpha1/flow_types.go`) and is executed by `flowrun_controller.go`, but a Flow with `action.type: wait` fails admission with:

```
must be one of http, transform, publish
```

**Impact:** Any user attempting to use wait steps in a Flow will receive a validation error even though the runtime supports it fully.

**Fix:** Add a `case "wait":` block to `validateFlowSpec()` in `flow_controller.go`.

**Scheduled:** Added to backlog in `docs/schedule.md`.

## TESTING GAP — No Ginkgo tests for `wait` step execution

**Location:** `internal/controller/flowrun_controller_test.go`

**Description:** The existing test suite covers HTTP steps (T7, T8), transform steps (T8), CEL skip cascades (T3), retries (T7), and GC (T4). There are no tests for `executeWaitStep` or the requeue-after-timeout behavior for wait steps.

**Impact:** Regression risk is high for any future changes to wait step handling.

**Fix:** Add Ginkgo test covering: (a) wait step reaches timeout → step transitions to Succeeded, (b) wait step with duration requeues with correct delay, (c) wait step within a multi-step flow doesn't block unrelated parallel steps.

**Scheduled:** Added to backlog in `docs/schedule.md`.

## TECH DEBT — CEL expression cache has no eviction policy

**Location:** `internal/controller/flowrun_controller.go` — `celProgramCache` (sync.Map, lines ~89–96)

**Description:** Compiled CEL programs are cached in an unbounded `sync.Map`. In long-running operators processing flows with many distinct `when` expressions, the cache grows without bound.

**Impact:** Slow memory leak in high-volume deployments. Not critical for typical usage (flows tend to reuse the same expressions).

**Decision needed:** See `docs/tech-debt/pending-input-required.md` — Q3.

## TECH DEBT — CEL environment init failure is permanently cached

**Location:** `internal/controller/flowrun_controller.go` — `celEnvOnce` / `celEnvErr` (~lines 89–96)

**Description:** The CEL environment is initialised with `sync.Once`. If initialisation fails (e.g. due to a transient dependency issue at startup), `celEnvErr` is set and all subsequent `when` expression evaluations fail forever — until the pod restarts.

**Impact:** Low probability (CEL env init is deterministic). If it does fail, all step conditions will evaluate to false, silently skipping all conditional steps. No alert is raised.

**Fix:** Log a high-severity error and trigger controller restart (or panic) on CEL env init failure, rather than silently degrading.

## TECH DEBT — Kafka producer pool has no TTL or health check

**Location:** `internal/controller/flowrun_controller.go` — `kafkaProducers` map (~lines 82–87, 1413–1443)

**Description:** `SyncProducer` instances are cached by broker address and never evicted. Stale connections after broker restarts or network topology changes are not detected until the next publish attempt fails.

**Impact:** Occasional publish failures that self-heal on retry. In environments with broker restarts, the first publish after restart will fail (triggering FlowRun step failure + retry), after which a fresh producer is created.

**Fix:** Add a per-producer last-used timestamp and periodically evict idle producers (e.g. unused for 10 minutes).

## TECH DEBT — HTTP Integration fetched from API server on every step

**Location:** `internal/controller/flowrun_controller.go` — HTTP step handler (~lines 696–799)

**Description:** Each HTTP step that references an `integrationRef` fetches the Integration object from the Kubernetes API server. For a 10-step Flow where all steps share the same integration, this generates 10 API calls per FlowRun.

**Impact:** Unnecessary API server load at scale. Not a correctness issue.

**Fix:** Cache integration lookups within a single `Reconcile()` invocation using a local `map[types.NamespacedName]*Integration`.

## BUG — Resource watcher context detached from manager lifecycle

**Location:** `internal/controller/resource_watcher.go:95`

**Description:** `context.WithCancel(context.Background())` creates a goroutine context with no parent — it is not cancelled when the manager shuts down. The watcher goroutine continues running after `mgr.Start()` returns, preventing clean shutdown.

**Impact:** Goroutine leak on shutdown; resource watcher cannot be gracefully stopped by the controller-runtime manager. In testing environments this causes test hangs waiting for goroutine cleanup.

**Fix:** Pass the manager's root context into `ResourceWatcher` at construction time (or use `mgr.Add()` to register it as a `Runnable`) and derive child contexts from it.

**Scheduled:** Added to `docs/schedule.md` §16 P1.

## BUG — Gateway Deployments missing health and readiness probes

**Location:** Gateway Deployment helpers (webhook, kafka, amqp, nats gateway constructors)

**Description:** Gateway pods have no `livenessProbe` or `readinessProbe` configured. Kubernetes cannot distinguish a crashed/deadlocked gateway from a healthy one and will not evict or restart it. All gateways expose a `/healthz` endpoint per the plugin contract — probes should target that.

**Impact:** Silent gateway failures go undetected. OperatorHub scorecard requires health probes on all managed Deployments.

**Fix:** Add `readinessProbe` and `livenessProbe` targeting `GET /healthz:8090` (or the gateway's configured port) to all gateway Deployment specs.

**Scheduled:** Added to `docs/schedule.md` §16 P1.

## BUG — Publish step does not capture response body on failure

**Location:** `internal/controller/flowrun_controller.go` ~line 899

**Description:** When a publish step receives a 4xx/5xx response the step is failed with a generic message. Unlike the HTTP step (which logs the truncated body at line 781), the publish step discards the response body entirely.

**Impact:** Publish failures cannot be debugged from FlowRun status alone. Users must add side-channel logging to their plugin to surface error details.

**Fix:** Read and capture up to 1KB of the error response body; include it in the step failure message, consistent with how HTTP steps handle failures.

**Scheduled:** Added to `docs/schedule.md` §16 P2.

## TECH DEBT — `goto` statement in FlowRun reconciliation loop

**Location:** `internal/controller/flowrun_controller.go` ~line 402 → label `allStepsDone` ~line 518

**Description:** A `goto allStepsDone` is used for early termination in the step execution loop. This violates modern Go style, makes the control-flow non-linear, and requires reviewers to trace the jump manually.

**Fix:** Extract the post-loop logic into a named function or replace the `goto` with a structured `for`/`break` or helper function.

**Scheduled:** Added to `docs/schedule.md` §16 P2.
